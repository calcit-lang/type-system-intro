# HM 与双向系统怎样配合

HM 和双向类型检查回答的侧重点不同。把它们放在同一张图里，比问“哪个更先进”更有帮助。

## 1. 核心对比

| 维度 | 经典 HM / Algorithm W | 基础双向系统 |
| --- | --- | --- |
| 主要目标 | 自动得到主类型 | 安排类型信息的两个流向 |
| lambda 参数 | 创建新变量后合一 | 通常从期望箭头类型获得 |
| 变量 | 查询方案并实例化 | 自然综合 |
| 函数应用 | 推断两边并合一 | 综合函数、检查参数 |
| 多态 | let 绑定处 rank-1 泛化 | 可通过标注扩展到 higher-rank |
| 标注需求 | 核心语言中通常很少 | 在不能综合或需要切换方向处出现 |
| 子类型扩展 | 会破坏简单的全局合一图景 | 可在综合转检查时集中处理 |
| 错误位置 | 可能在远处约束冲突时暴露 | 往往更靠近期望与实际不符处 |

这张表比较的是典型教学版本。真实编译器往往是混合系统。

## 2. 同一个 lambda 的两种处理

表达式：

```text
fn x => x
```

### HM

1. 为 `x` 创建 $\alpha$；
2. 函数体 `x` 得到 $\alpha$；
3. lambda 得到 $\alpha\to\alpha$；
4. 若位于可泛化边界，得到 $\forall\alpha.\alpha\to\alpha$。

信息主要从表达式内部向外生成。

### 基础双向

裸 lambda 不能综合。若已知期望类型 `Int -> Int`：

1. 将输入 `Int` 绑定给 `x`；
2. 按 `Int` 检查函数体；
3. 整个 lambda 检查成功。

信息主要从外部期望向内传播。

### 混合系统

很多实用系统在没有期望类型时为 lambda 参数创建元变量，有期望箭头类型时优先利用它。此时既有双向结构，也使用 HM 风格的合一工具。

## 3. let 多态仍然可以放进双向框架

可以设计综合规则：

$$
\frac{
  \Gamma\vdash e_1\Rightarrow A
  \qquad
  \sigma=\operatorname{generalize}(\Gamma,A)
  \qquad
  \Gamma,x:\sigma\vdash e_2\Rightarrow B
}{
  \Gamma\vdash
  \texttt{let}\;x=e_1\;\texttt{in}\;e_2
  \Rightarrow B
}
$$

若 $e_1$ 本身不能综合，可以要求注解，或提供一个按外部期望检查 `let` 的规则。双向性没有取消 let 泛化，只是要求明确每一步的信息方向。

## 4. principal type 与 annotations 的取舍

HM 的主类型性质让编译器能说：“我推断出了所有合法类型中最一般的那个。”

更强系统未必总存在方便计算的主类型。例如表达式可能同时适合多个无法由单一最一般类型概括的子类型分支，或 higher-rank 推断本身不可判定。

双向系统常做的工程取舍是：

> 不承诺在所有位置猜出最一般意图；在信息不足的边界要求程序员写下类型，然后完整地检查它。

这不是推断算法“失败”，而是语言可预测性契约的一部分。

## 5. 为什么 higher-rank 常需要双向标注

考虑：

```text
fn f => (f(1), f(true))
```

它至少有两种可能意图：

1. `f` 是单态函数，那么两次调用冲突；
2. `f` 是 `forall a. a -> a`，那么两次调用合法。

只看函数体，检查器是否应该自动选择第二种极强承诺并不明显。注解：

```text
(fn f => (f(1), f(true)))
  : (forall a. a -> a) -> (Int, Bool)
```

把意图放在 higher-rank 边界，双向检查负责验证，而不是全局猜测。

## 6. 错误信息的差异

例子：

```text
let render: User -> String =
  fn user => user.age + 1
```

双向检查从声明得到返回类型 `String`，函数体却综合出 `Int`，可以在函数体结尾报告：

```text
expected String, found Int
while checking the body of render
```

纯约束式推断可能先传播更多约束，最终在某个使用点发现 `Int = String`。良好的约束来源追踪也能生成优秀错误；双向结构只是天然提供了明确的“expected/actual”边界。

## 7. 实际语言中的常见组合

一个现实的组合策略可能是：

1. 局部表达式采用 `synth`/`check` 两个入口；
2. 可综合位置创建存在型元变量；
3. 使用合一或有方向的实例化求解元变量；
4. `let` 或模块定义处做受限制的泛化；
5. higher-rank、递归、多态递归或复杂子类型边界要求标注；
6. 每个约束保留源位置和期望来源。

因此实现代码里同时出现 `generalize`、`instantiate`、`unify`、`synth` 和 `check` 完全合理。

## 8. 怎样判断某篇论文采用哪种策略

先找判断式定义：

- 只有 $\Gamma\vdash e:A$：可能是声明式单向系统；
- 有 $\Rightarrow/\Leftarrow$：明确双向；
- 判断返回 $S$：可能显式传替换；
- 有输入/输出上下文：可能用有序上下文管理存在变量；
- 有约束 $C$：可能分离约束生成与求解；
- 有 $\forall$ 引入/消去规则：观察量词在什么方向处理；
- 有 $<:$ 或 instantiation judgment：不要把它当普通类型相等。

## 9. 选择实现路线

如果目标语言只需要 ML 风格 rank-1 let 多态，先实现 HM/W 或 J 通常最直接。

如果目标包括显式签名、higher-rank 参数、子类型、GADT 或依赖类型，双向结构通常是更稳妥的骨架。

如果目标是面向用户的完整语言，常见答案不是二选一，而是：

- 用双向判断控制局部信息流；
- 用 HM 的自由变量、实例化、泛化和合一工具解决允许自动推断的部分；
- 用标注划出不可或不应自动猜测的边界。

## 10. 一句总结

HM 的明星能力是“在受限多态范围内推得最一般”；双向系统的明星能力是“让已知信息与未知信息沿正确方向相遇”。理解两者后，就能看懂现代类型检查器为什么既会猜，也会要求标注。

## 本章检查点

- 能说明 HM 与双向检查不是同一维度的二选一。
- 能判断某条规则是在全局求解约束，还是传播局部期望类型。
- 能解释为什么复杂特性常要求标注，而简单局部仍可自动合一。
- 能为一个小语言划出“推断、检查、必须标注”的边界。
